# Security review of 9 November 2026: what we found and fixed

On 9 November 2026 we received an AI-generated (ChatGPT) security review
of FeroSSH at commit `5f949f3`. The report is kept as received in
[2026-11-09-ai-review.md](2026-11-09-ai-review.md). Because no human
auditor wrote it, we took nothing in it as fact: we checked each finding
in our source and, for dependencies, in the published crate sources and
the upstream IronRDP issue tracker.

All findings below are fixed or decided in FeroSSH main since
9 November 2026 (pull requests #126 to #131, and #135 to #138 after a
second review; see [Re-audit](#re-audit-of-ed3aabe)). The first release that has
them is the one after v1.2.0.

## Findings

| ID | Report says | What we found | Fix |
|---|---|---|---|
| FSSH-01 | The built-in RDP viewer never checks the server's certificate | True in the code, but not reachable. The built-in viewer is only opened for a desktop on the SSH server itself (`localhost`), which the SSH host key already authenticates. RDP through a bastion (`Via`) goes to mstsc.exe, which checks the certificate itself. | #127 makes the localhost-only rule explicit: the viewer refuses any other host. |
| FSSH-02 | VNC is unencrypted between a bastion and another target; "None" is preferred over VNC authentication | Confirmed. | #128: the viewer prefers VNC authentication when the server offers it, says when a desktop has no password, and asks once before a VNC desktop whose last leg (bastion to target) is unencrypted. |
| FSSH-03 | IronRDP reassembles dynamic channel messages without a limit | Confirmed. `ironrdp-dvc` trusts the length a server announces (up to 4 GiB). Upstream issue [IronRDP#2092](https://github.com/Devolutions/IronRDP/issues/2092) is open; 0.10.0 is unchanged. The viewer's 1 GiB memory cap contained it to the desktop tab. | #129: the viewer checks each channel PDU before IronRDP sees it and ends the session when a dynamic channel message announces more than 1 MiB. A header split over chunks slipped past it until #135 (FSSH-09 below). |
| FSSH-04 | Desktop IPC queues are unbounded | Confirmed. If the viewer stalled, the window process (which has no memory cap) could grow. | #130: the window holds at most 4 MiB of queued desktop bytes and makes the network reader wait; the viewer's input queue holds 64 events. |
| FSSH-05 | `pageant 0.2.4` has an advisory | Partly. `0.2.5` adds a length check on requests FeroSSH writes to Pageant, which only matters with agent forwarding; FeroSSH has none. We found no published advisory. | #131 updates to `pageant 0.2.5` anyway. |
| FSSH-06 | IronRDP does not bound compressed static channel chunks | Confirmed in IronRDP ([IronRDP#2081](https://github.com/Devolutions/IronRDP/issues/2081), open; 0.10.0 unchanged). The viewer never asks for compression, but a server could still set the flag. | #129: compressed channel data ends the session, and a static channel message over 8 MiB too. |
| FSSH-07 | Desktop passwords show in `Debug` output and are copied into plain strings | Partly. Nothing logged them, and the viewer already wiped its own copies. | #131: desktop passwords travel in a type that prints as `Secret(..)` and is wiped on drop, and the IPC buffers that carry them are wiped too. One copy remains: IronRDP's `Credentials` takes a plain `String`. |
| FSSH-08 | Desktop clipboard sharing is on by default | True, by design at the time. | #126: the desktop and remote-app clipboard are now off until you turn them on. |

## Re-audit of ed3aabe

After #126 to #131 merged, a second AI-generated (ChatGPT) review looked
at main at `ed3aabe`. It agreed the findings above were dealt with, and
raised four more. We checked each in the code:

| ID | Report says | What we found | Fix |
|---|---|---|---|
| FSSH-09 | The dynamic channel cap can be skipped by splitting the DataFirst header over static chunks | Confirmed. The guard read the header only from a message's first chunk; a shorter first chunk passed, and IronRDP reassembled the header. The impact was that of FSSH-03: the viewer's 1 GiB cap ends the desktop tab. | #135: the guard keeps the header's first 9 bytes across chunks and checks them once complete; tested by splitting at every byte and through IronRDP's own reassembly. |
| FSSH-10 | The 4 MiB queue budget counts bytes, not messages | Confirmed. Many one-byte reads while the viewer is stalled could queue millions of small messages in the window. | #136: each queued message also counts 256 bytes, and no message may exceed `MAX_NET`. |
| FSSH-11 | The RDP password is still copied into a plain `String` | Confirmed; the same leftover noted under FSSH-07. IronRDP's `Credentials` takes a `String` and does not wipe it. | None in FeroSSH; it needs a change in IronRDP. |
| FSSH-12 | The unencrypted-VNC approval is kept by connection name, not endpoint | Confirmed. Editing a connection's host while FeroSSH ran kept the approval. | #137: the approval is kept by connection, host, port and SSH server. |

Three more points came from our own reading of the fixes:

- The password typed at a desktop prompt grew one character at a time,
  leaving copies of its start in freed memory. #138 gives it room for
  256 bytes up front and never grows it.
- A virtual desktop's VNC server, which FeroSSH starts with a password,
  that then offers no authentication may have had the password option
  removed on the way. #138 ends that session instead of warning.
- IronRDP's own copy of the RDP password (FSSH-11) stays.

## Not checked

The first report gives CVE numbers for the russh issues fixed in russh
0.65.1 (CVE-2026-116773 and CVE-2026-116774), and the re-audit one for
the pageant issue fixed in 0.2.5 (CVE-2026-116775). We did not check
those numbers.
FeroSSH has used russh 0.65.1 since PR #122.

## Possible later work

- VeNCrypt (TLS) for VNC, so the last leg through a bastion can be
  encrypted.
- Offering the reassembly limits to IronRDP upstream, then dropping the
  viewer's own checks once a fixed release is out.
- Asking IronRDP for a credential type that wipes the password (FSSH-11).
