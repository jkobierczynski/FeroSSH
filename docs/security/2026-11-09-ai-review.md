# Part II — FeroSSH Security Review

**Review date:** 9 November 2026  
**Inspected commit:** `5f949f3426472a266ac99d3f0b7ff35dd6e07fd3`  
**Comparison baseline:** `c193afe5ba858e1aa076cf7a708c4ed168d16790`  
**Language:** Rust  
**Scope:** SSH transport/dependencies, Windows desktop viewer, RDP, VNC, IPC, process isolation, clipboard and password handling.

> **Scope limitation:** This was a source-level and dependency review of the specified commit. It was not a Windows penetration test, runtime exploit reproduction, formal protocol audit, or full fuzzing campaign. RDP/VNC findings apply to builds that include the optional desktop-viewer functionality.

## 1. Executive assessment

The reviewed commit contains meaningful security improvements. In particular, it upgrades `russh` from 0.64.1 to 0.65.1, resolving the previously identified `russh` issues associated with CVE-2026-116773 and CVE-2026-116774. The new desktop functionality also includes useful process isolation, IPC validation, size limits and a VNC decoder fuzz target.

The main risks are concentrated in the newly added remote-desktop paths:
- RDP server certificate verification is disabled.
- VNC may rely on an SSH tunnel that does not actually protect the bastion-to-target leg when the desktop target is a different host.
- IronRDP dynamic-channel reassembly may permit unbounded memory growth from a malicious server.
- Desktop IPC uses unbounded queues without an explicit byte budget.

**Overall assessment: Medium risk.** The conditional risk becomes **High** when the built-in remote desktop client connects through an SSH bastion to a separate RDP/VNC target.

No confirmed remote code execution or sandbox escape was identified in this review.

## 2. Findings

### FSSH-01 — RDP TLS certificate verification is disabled

**Severity: High, conditional on network topology**

**Relevant file:** `crates/viewer/src/rdp.rs`, approximately lines 417–459  
**Routing context:** `crates/app/src/win.rs`, approximately lines 8718–8785

The RDP client uses a custom Rustls certificate verifier that accepts any server certificate (`ServerCertVerified::assertion()`). It does not validate the certificate chain or verify that the certificate belongs to the intended RDP host.

The implementation assumes that the SSH tunnel terminates on the same machine as the RDP server. However, the desktop-session routing code can use the configured target hostname when a `Via` SSH connection is selected. In that case, the SSH host key authenticates the bastion, not the separate RDP target.

**Potential impact:** An attacker on the bastion-to-target network path, or a compromised bastion, may impersonate the RDP endpoint. The client may establish CredSSP/TLS with that endpoint despite not validating its identity. In the xrdp fallback path, credentials may be sent to the impersonating endpoint.

**Recommended fix:**
- Validate the RDP server certificate chain and hostname against a configured trust store.
- Support certificate pinning or a trust-on-first-use workflow.
- Bind trust decisions to the actual target hostname and port.
- Do not treat SSH authentication of a bastion as authentication of a different RDP server.

### FSSH-02 — VNC encryption assumption fails for a separate `Via` target

**Severity: High, conditional on network topology**

**Relevant file:** `crates/viewer/src/vnc.rs`, approximately lines 554–585

The VNC client supports security type 1 (None) and type 2 (VNC Authentication), rejects TLS alternatives, and relies on the assumption that the SSH tunnel encrypts the connection.

When the SSH connection terminates at a bastion and the VNC server is a different host behind it, the bastion-to-target connection is not protected by the client-to-bastion SSH tunnel. VNC screen contents, input and authentication exchanges may therefore be exposed on that second network leg.

The client also selects `None` before VNC Authentication when both are offered.

**Recommended fix:**
- Support VeNCrypt/TLS or another authenticated encrypted VNC transport.
- Alternatively, establish a second SSH tunnel to the actual VNC target.
- Prefer VNC Authentication when a password is configured.
- Require explicit user approval for no-authentication VNC.
- Make the real encryption boundary visible in the UI/documentation.

### FSSH-03 — IronRDP dynamic-channel reassembly may be unbounded

**Severity: Medium — remote denial of service**

**Relevant dependency:** `ironrdp-dvc 0.9.0`  
**Relevant file:** `crates/viewer/src/rdp.rs`, around the dynamic-channel client setup

The reviewed dependency version is affected by an upstream IronRDP issue describing incomplete dynamic-channel messages that can grow without bound. The relevant reassembly logic records a declared total size and appends fragments without an adequate independent maximum.

FeroSSH uses the dynamic virtual channel client with the Display Control client. A malicious RDP server may be able to declare a very large message and send fragments that cause memory growth in the viewer process.

**Mitigation:** The viewer process is isolated and has a 1 GiB memory limit. This limits the likely blast radius to the viewer/session rather than the main application, but does not remove the denial-of-service issue.

**Recommended fix:**
- Upgrade to a release that enforces a strict reassembly cap, or patch/vendor the dependency.
- Enforce per-message and per-session byte budgets.
- Reject oversized declared lengths before allocating or appending.
- Add malformed-fragment regression tests and fuzzing.

Upstream reference: [IronRDP issue #2092](https://github.com/Devolutions/IronRDP/issues/2092).

### FSSH-04 — Unbounded desktop IPC queues

**Severity: Medium — resource exhaustion / backpressure**

**Relevant file:** `crates/app/src/desktop.rs`, approximately lines 141–189

The desktop IPC path creates an unbounded `mpsc::channel::<ToViewer>()`. The network reader can enqueue chunks up to approximately 1 MiB. If the viewer or pipe writer is slower than the network reader, queued data can grow without an explicit byte budget or backpressure mechanism.

A related unbounded channel exists in the viewer RDP input path. The viewer's process memory cap mitigates viewer-side impact, but the main application-side queue is not protected by the viewer's job-object limit.

**Recommended fix:**
- Replace unbounded channels with bounded channels.
- Add byte accounting, not only message-count limits.
- Apply backpressure or terminate the session when a queue budget is exceeded.
- Separate latency-sensitive control messages from bulk frame/data messages.
- Add stress tests with a deliberately slow consumer.

### FSSH-05 — Pageant dependency advisory remains outstanding

**Severity: Medium/Low — dependency hardening**

**Dependency:** `pageant 0.2.4` in `Cargo.lock`  
**Affected use:** Local SSH agent client integration in `crates/auth/src/agent.rs`

The reviewed lockfile still contains `pageant 0.2.4`; the reported advisory is fixed in `0.2.5`. The issue concerns trusting a peer-controlled four-byte length and potentially allocating without a bound.

The inspected code uses Pageant as a local SSH agent client. No agent-forwarding implementation was identified in the inspected worker/session path, so the exact remote attack route described by the advisory was not demonstrated for FeroSSH. Nevertheless, the dependency should be updated.

**Recommended fix:** Update to `pageant >= 0.2.5` and add a regression test for oversized agent response lengths.

### FSSH-06 — Investigate IronRDP static-channel compressed-fragment handling

**Severity: Investigate — potential remote denial of service**

**Dependency:** `ironrdp-svc 0.9.0`

An upstream IronRDP issue reports that compressed static-channel fragment handling may not enforce the declared length and can accumulate data until the final fragment. Reachability depends on the negotiated channel and compression behavior.

This was not established as a directly exploitable FeroSSH vulnerability during the review. Treat it as a dependency risk requiring a reachability check and regression test, rather than a confirmed exploit.

Upstream reference: [IronRDP issue #2081](https://github.com/Devolutions/IronRDP/issues/2081).

### FSSH-07 — Password handling and debug exposure

**Severity: Low/Medium — secret hygiene**

**Relevant files:** `crates/viewer/src/pipe.rs`, approximately line 69; `crates/viewer/src/rdp.rs`, approximately line 243

The `ToViewer::Password(Vec<u8>)` IPC enum derives `Debug`, which means formatting the enum with `Debug` can expose password bytes. No active logging path doing so was identified in the reviewed code, but the type makes accidental disclosure easier.

The RDP path also copies the password into an ordinary `String`.

**Recommended fix:**
- Implement redacted `Debug` output or remove `Debug` from secret-bearing types.
- Minimize password copies.
- Zeroize temporary buffers after authentication where the API permits.
- Ensure errors and tracing never include credentials.

### FSSH-08 — Clipboard defaults deserve a security-conscious choice

**Severity: Informational / configuration hardening**

The inspected configuration path defaults clipboard directions to enabled when no explicit value is provided. Bidirectional clipboard sharing can leak sensitive data or introduce untrusted content across the remote-desktop boundary.

The recent FeroStream changes are positive: they add clipboard direction controls, a 1 MiB cap, X11 INCR support, explicit mouse-selection opt-in, a fuzz target, and fail-closed agent state until rules arrive.

**Recommended improvement:** Consider default-off clipboard sharing for new/untrusted desktop connections, or prompt for direction explicitly. Document the implications and provide simple per-session controls.

## 3. Positive security controls

The reviewed implementation includes several strong mitigations:
- Windows AppContainer process isolation.
- A 1 GiB process memory limit.
- No network, filesystem, registry or clipboard process capabilities granted to the viewer.
- IPC framing and input validation.
- Limits on frame, clipboard and screen dimensions.
- A VNC decoder fuzz target.
- Explicit clipboard direction controls and size limits in the FeroStream changes.

The RDP `checked_size()` path validates dimensions before allocating a decoded image, which helps mitigate oversized server-supplied desktop dimensions.

The `russh` upgrade from 0.64.1 to 0.65.1 resolves the previously identified issues:
- CVE-2026-116773 — unbounded EXT_INFO handling.
- CVE-2026-116774 — zero maximum packet-size handling.

The `pageant` dependency remains at 0.2.4 and should be updated to at least 0.2.5.

## 4. Recommended remediation order

**Priority 0 — Remote-desktop endpoint trust**
1. Implement RDP certificate validation or pinning for the actual target.
2. Correct the VNC encryption model for `Via`/bastion connections.
3. Do not silently prefer unauthenticated VNC when stronger offered options exist.

**Priority 1 — Memory and resource limits**
4. Patch/upgrade IronRDP DVC reassembly to enforce strict caps.
5. Investigate and test IronRDP SVC compressed-fragment handling.
6. Replace unbounded desktop IPC queues with byte-budgeted bounded queues.

**Priority 2 — Dependency and secret hygiene**
7. Update `pageant` to at least 0.2.5.
8. Redact password-bearing `Debug` output.
9. Minimize and zeroize temporary password copies.
10. Reconsider clipboard defaults for untrusted hosts.

## 5. Overall FeroSSH assessment

**Overall risk: Medium.**  
**Conditional risk: High** when the built-in RDP/VNC client connects through an SSH bastion to a different desktop target.

The SSH transport/dependency position improved with the `russh` upgrade. The new viewer isolation is a good architectural decision and materially reduces the impact of a viewer compromise or memory-exhaustion event.

The most important design flaw is the mismatch between the assumed and actual trust boundary: SSH authenticates the bastion, while RDP/VNC may connect onward to another host. The remote-desktop protocols need their own endpoint authentication and encryption guarantees.

No confirmed RCE or sandbox escape was found in this source-level review. Findings involving upstream IronRDP behavior should be validated against the exact dependency code and negotiated protocol paths.
