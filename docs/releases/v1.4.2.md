# FeroSSH v1.4.2

*Secure connections. Forged in Rust.*

FeroSSH 1.4.2 is a security release. It closes the findings of a fresh audit of the whole code base: host keys, X11 forwarding, WinRM over HTTP, network shares, programs started by name, downloads, the RDP viewer and port forwards. There are no new features, but one change can stop an existing WinRM connection from logging in; see **Before you upgrade**. If you're new to FeroSSH, the [1.0 release notes](https://github.com/jkobierczynski/FeroSSH/releases/tag/v1.0.0) are the place to start.

## Before you upgrade

- **WinRM over plain HTTP now logs in with Kerberos only.** NTLM over HTTP doesn't prove who answers, so a machine in the middle could collect or relay your Windows logon's NTLM response. A WinRM connection over HTTP (port 5985) to a server named by its address, a workgroup server or a local account, which used to fall back to NTLM, now stops with a message saying why. Use HTTPS (`winrms://`), the server's domain name so Kerberos is used, or set the connection's *Transport* to *HTTP, Kerberos or NTLM (5985)* if you accept the risk on that network.

## Security

- **Host keys.**
  - A `known_hosts` file that exists but can't be read used to count as empty, so a pinned host looked new. With `StrictHostKeyChecking accept-new` a different key was then trusted without asking. Now the host key is refused, with the file named. Files written as UTF-16 by Windows PowerShell's `>` and `>>` are read correctly, and a bad byte only costs its own line.
  - A server offering a key of another type than the one(s) pinned for it now gets the full **HOST KEY CHANGED** block, with no prompt, like a changed key. This is stricter than OpenSSH, which asks yes or no.
- **X11 forwarding.** The window now checks every X connection's cookie itself and swaps in the real one only then. The sandboxed worker only ever sees a fake cookie, and connections it makes up are refused. X11 forwarding is still off unless a host turns it on.
- **Nothing is opened on network shares.** An `IdentityFile`, `CertificateFile` or `UserKnownHostsFile` path on a share (`\\server\...`) is never opened, because Windows would sign in to that server as you. An imported connection with a key on a share leaves the key out and says so. Keys on a mapped drive letter still work.
- **Programs started by name.** `ProxyCommand` and password commands are now started from System32, the Windows folder or absolute `PATH` folders, never from the folder `ferossh.exe` sits in (often Downloads), as local shells already were.
- **Downloads.**
  - Files downloaded over SFTP or ZMODEM are marked as from the Internet (Mark of the Web), so SmartScreen checks a downloaded program and Office opens documents in Protected View.
  - With ZMODEM on, a receive started by the server now asks first instead of writing into Downloads straight away.
- **RDP certificates are pinned.** The built-in RDP viewer (`ferossh-desktop.exe`) remembers each desktop's TLS certificate the first time. If it changes, the viewer stops before the login and shows the new fingerprint, so another program listening on that port can't receive your login.
- **Port forwards only serve your own Windows session.** Local (`-L`) and SOCKS (`-D`) forwards listening on loopback now refuse connections from other users signed in to the same PC and from services. Your own programs, elevated ones too, still work.
- **Smaller fixes.**
  - The approval dialogs for scripts on Production, password and secret tools and `ProxyCommand` now strip text-direction characters, so a dialog can't show one program's name while another runs.
  - A terminal grid is capped at 2048 × 1024 cells, so a server asking tmux for a huge window can't exhaust memory and close every tab.
  - A burst of OSC 52 clipboard requests now asks about only the last one per pane.
  - Two remote files that map to the same local name no longer share a partial download file.

## For maintainers

- Release builds now leave out the linker's Rich header (`/emittoolversioninfo:no`), so a Microsoft servicing update of `link.exe` no longer changes the exes' bytes and fails the reproducible build check. `build-release.ps1` refuses an exe that still has one. When a rebuild differs, the reproducible job now says which part of the exe differs.
- In `release.yml`, the update signing key is no longer in the environment while anything compiles: the signer is built first and then run. Every GitHub Action in the workflows is pinned to a commit SHA, with its tag as a comment.
- Tag with git on your PC (`git tag v1.4.2 <merge commit> && git push origin v1.4.2`), then run `pwsh scripts/sign-release.ps1 -Tag v1.4.2` (PowerShell 7, GitHub CLI 2.93 or later).

## Downloads

| File | What it is |
| --- | --- |
| `ferossh.exe` | The standard client. |
| `ferossh-desktop.exe` | The same client plus a built-in RDP and VNC viewer that shows a remote desktop in a FeroSSH tab, in a sandboxed viewer process. |
| `ferossh-arm64.exe`, `ferossh-desktop-arm64.exe` | The same two for Windows on ARM. |
| `ferostream-agent` | The FeroStream agent for 64-bit Intel and AMD Linux hosts, for remote apps. Keep it next to the exe. |
| `ferostream-agent-aarch64` | The same agent for 64-bit ARM Linux hosts, such as a Raspberry Pi. |

The Linux agents are not code signed, but `SHA256SUMS.txt` and the build provenance cover them as well. To build them yourself, see [FeroStream agents](https://github.com/jkobierczynski/FeroSSH#ferostream-agents) in the README.
