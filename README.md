# FeroSSH

*Secure connections. Forged in Rust.*

FeroSSH aims to be the smallest, most secure open-source SSH client for Windows: a native PuTTY replacement with tabs, splits, tmux integration and file transfer, shipped as one signed exe with nothing to install.

> **Status:** working toward 1.0 ([v0.1.0](https://github.com/jkobierczynski/FeroSSH/releases/tag/v0.1.0) is out). FeroSSH connects with russh from one sandboxed worker process per connection, checks host keys against `~/.ssh/known_hosts`, and signs in with the Windows OpenSSH agent, Pageant, key files, FIDO2 security keys, keyboard-interactive or a password. It has tabs and splits, saved sessions with imports from PuTTY, KiTTY, WinSCP, MobaXterm, mRemoteNG and SecureCRT, password sources, jump hosts (`ProxyJump`, `ProxyCommand`), SFTP and ZMODEM file transfer, port and X11 forwarding, tmux integration, serial consoles, Telnet for old gear, broadcast input, login scripts and command snippets, remote desktops through SSH, and sealed session logs.

The [user guide](docs/guide/README.md) covers getting started, everyday use, every setting, the security model, verifying a download and troubleshooting.

## Download

Download `ferossh.exe` from the [latest release](https://github.com/jkobierczynski/FeroSSH/releases/latest) (or `ferossh-exe` from the latest CI run for the newest changes) and start it with a host, or without one to be asked. Release exes are not code signed yet, so Windows SmartScreen may warn the first time you run one; [Verifying a download](docs/guide/verifying-downloads.md) shows how to check it against `SHA256SUMS.txt` and its build provenance attestation instead (see [Code signing](#code-signing)).

```
ferossh.exe [user@]host[:port]
ferossh.exe -l user -p 2222 host
ferossh.exe myalias            # a Host from ~/.ssh/config
ferossh.exe COM3:115200       # a serial console
ferossh.exe telnet://router   # Telnet (unencrypted), port 23 unless given
ferossh.exe --local [command]  # a local shell
ferossh.exe --check-sandbox    # report what the sandbox can do on this PC
```

`HostName`, `User`, `Port`, `IdentityFile`, `Tag`, `Include`, `ProxyJump`, `ProxyCommand` and the forwarding keywords (`LocalForward`, `RemoteForward`, `DynamicForward`, `ForwardX11`, `GatewayPorts`, `ClearAllForwardings`) are read from `~/.ssh/config`.

- **Tabs and splits.** The window starts with one pane and no tab strip. Ctrl+Shift+T opens a tab, Alt+Shift+= and Alt+Shift+- split the pane; the tab strip appears once there are two tabs. A new tab or pane on a host you are already logged in to opens another channel on the same connection, so there is no second login. Drag a divider to resize, drag a tab to reorder, and Ctrl+Shift+drag a pane onto another pane's edge to move it there (or its middle to swap them). To merge a tab back in as a pane, drag the tab down out of the strip onto a pane of the tab that appears (move back up over another tab first to pick that one), or use Window > Join tab into the tab before it (Ctrl+Shift+J); dropping a pane on the tab strip makes it a tab again, and holding it over a tab shows that tab, to drop the pane into it.
- **Serial consoles.** Type a COM port at the connect prompt (`COM3`, `COM3:115200`, `COM3:9600,7E1,xonxoff`) or on the command line, or make a session of type *Serial console* in the session form, with the port, speed, framing (8N1, 8E1, 8O1, 7E1, 7O1, 8N2) and flow control (none, XON/XOFF, RTS/CTS, DSR/DTR). What is left out is 9600 8N1 without flow control, the usual console default of switches and routers. Session > Send break holds the line in break for 300 ms (ROM monitor on Cisco gear, SysRq on Linux). The port is opened by the FeroSSH window itself, not the sandboxed SSH worker, which cannot reach devices. Unplugging a USB adapter ends the session with a note; Enter opens the port again. Logs, themes and broadcast input work as for SSH tabs.
- **Telnet**, for old switches, routers and console servers that have nothing better. Type `telnet://host[:port]` or `telnet host port` at the connect prompt, or make a session of type *Telnet (unencrypted)* in the session form (port 23 unless you give one). Telnet sends everything in the clear, passwords included, so the pane says so when it connects and the tab carries a red **⚠ telnet** badge. The connection runs in a sandboxed worker of its own, like an SSH connection, and the Telnet option parser there is fuzz-tested. FeroSSH agrees only to binary mode, echo, suppress-go-ahead, terminal type (`xterm-256color`) and window size (sent again on every resize), and refuses every other option; it never sends environment variables or a user name. SFTP, forwards, tmux and remote desktops are SSH-only. Logs, themes and broadcast input work as for SSH tabs.
- **Broadcast input.** Window > Broadcast input to this tab's panes (Ctrl+Shift+B) sends what you type and paste in the focused pane to the other panes of the tab as well; Broadcast input to all tabs reaches every pane. Each pane encodes the keys itself, so arrow keys work in vim in one pane and the shell in another. Every pane that receives is framed in amber and the window title says broadcast is on. Window > Leave this pane out of broadcast keeps one pane to itself. Only panes that pass typing straight to their host take part: nothing typed at a password prompt or the connect prompt is broadcast, and a pane waiting at one never receives other panes' keys. A paste with line breaks always asks first while broadcast is on, and says how many panes it goes to.
- **Login scripts.** A session's Extras section in the session form holds a login script, one step per line, for devices that need answers after the login: `expect Username:` waits up to 15 seconds for that text, `send terminal length 0` types a line and Enter (`send` alone is just Enter), `password` types the session's login password from its password source, `secret enable` types a named secret, and `pause 2` waits. It runs once after an SSH login or when a serial port opens; tmux attaches after it. Secrets are never written to a FeroSSH file: the first time, the pane asks for one (without echo) and keeps it in the Windows Credential Manager as `FeroSSH secret:<name>`, or a `Secret` block in `ferossh.conf` names a password manager command for it (`%n` is the secret's name). Pressing any key stops the script, and Session > Run login script again starts it over. What the script types is never broadcast.
- **Command palette.** Ctrl+Shift+A (View > Command palette) is one search box over every menu action, every session and every command snippet. Type a few letters in any order (`splr` finds Split right, `core` your core switch, `ctrl+shift+n` the action on that key), then Enter runs the action, connects to the session or types the snippet; Shift+Enter connects in a split or types a snippet without its last Enter. Each action shows its shortcut and check mark, greyed-out menu items are left out, and the last few picks come first. Esc closes it.
- **Command snippets.** Ctrl+Shift+Space (View > Command snippets) lists named command lines. Type to filter, then Enter types the snippet with Enter after each line, or Shift+Enter leaves the last line for you to finish; with broadcast input on it goes to every broadcast pane too. Insert adds a snippet (what you typed as a filter becomes its name), F2 edits one, Delete removes one; Edit > Save selection as snippet starts one from text selected in a pane, and Ctrl+Shift+V pastes into the editor (several lines become several snippet lines). A snippet can take arguments: `$1` to `$9`, or `${1:Gi0/1}` with a default. Running it first asks for the values in the side pane, prefilled with the defaults, and shows what will be typed; Enter moves to the next value and types on the last. `$$` types a plain `$`, so `awk '{print $$1}'` stays `awk '{print $1}'`; other `$` text such as `$HOME` is left alone. Snippets are kept in `ferossh.conf`.
- **Snippet macros.** A snippet line can be a step: `@expect (config)#` waits for the host, `@capture Version *,` keeps a value from the reply, `@pause 2`, `@key enter` (or `space`, `tab`, `escape`, `ctrl+z`), `@type y` (no Enter), `@password` and `@secret enable`; `@@` types a plain `@`. Variables fill themselves in: `${session}`, `${host}`, `${user}`, `${port}`, `${date}`, `${time}`, `${stamp}` (for file names) and `${clipboard}`, so `copy run tftp://10.0.0.5/${host}-${stamp}.cfg` needs no typing (`${HOME}` and other names are left alone). In the editor a snippet can be kept to some hosts (`sw-* core-?`) or session-manager folders; those for the focused pane's host are listed first, the others dimmed, and the command palette shows only the ones that apply. A snippet can have a hotkey, Ctrl+Shift+F1 to F12. Run on several panes (broadcast), or with `@capture` steps, it shows a live report in the side pane: one row per host with its state and captured values, which Enter copies as a table for a spreadsheet.
- **Auto-responses.** A snippet's *When* text makes it answer by itself whenever the host prints that text, for example `@key space` when `--More--` appears, or `@key enter` on `[confirm]`, on the hosts it is kept to. The host only decides *when*: an auto-response types only lines and keys you wrote, never a password, a secret, the clipboard or arguments, and after 20 answers in one second it pauses until you type. Session > Auto-responses from snippets turns them all off.
- **Production guard.** A snippet about to be typed into a pane with the red Production theme (by a theme rule, the `production` tag or by hand) asks first, listing the hosts and the lines. Session > Confirm snippets on Production hosts turns it off.
- **Recording.** Edit > Record keystrokes as snippet records what you type in the focused pane until you pick it again, then opens it in the snippet editor to name and check. Backspace, Ctrl+U and Ctrl+W edit lines as a shell does, Tab and Ctrl+ keys are kept as `@key` steps so tab completion replays, and a line the host did not echo back (a password) is recorded as `@password`, never as its text.
- **Session manager.** Ctrl+Shift+S shows the hosts from `~/.ssh/config` in a side pane, hidden by default. Type to filter, Enter connects in this tab (Shift+Enter in a split), Ctrl+D marks a favourite. A `# folder: Name` comment above a `Host` groups hosts. View > Side pane on right moves it; drag its edge to resize it.
- **Saved sessions.** No ssh_config needed: "+ New session" at the top of the session manager (or Insert) opens a form in the side pane, and F2 (or a right click) edits the selected session. The form has a name, folder, host or IP address, user, port, key file (with Browse…), password source and jump host, then a Look section (theme, font, size, scrollback) and an Extras section (tmux session, port forwards such as `L 8080 localhost:80`, RDP and VNC ports, older crypto). Empty fields show their default in grey; Enter saves, Shift+Enter saves and connects, Esc cancels, Del deletes a saved session after asking. Sessions go to `%APPDATA%\FeroSSH\sessions.conf` in ssh_config syntax and their look to `ferossh.conf`. Hosts from `~/.ssh/config` and the imports show their connection settings read-only (FeroSSH never writes those files); their look and extras can still change, and a new name saves an editable copy.
- **Passwords without typing.** Keys and agents need no password at all; the Windows OpenSSH agent pipe also serves the 1Password and Bitwarden SSH agents, whose keys stay in the vault. For servers that want a password, the session form's Password field picks where it comes from. *Windows Credential Manager* saves the password the first time a login with it works (as `FeroSSH:user@host:port`, protected by your Windows sign-in, on this PC only) and fills it in from then on. *1Password*, *Bitwarden* or *KeePassXC* fill in a command for that tool's CLI (`op`, `bw`, `keepassxc-cli`) that you can edit, or write *a command of your own*; `%n` is the session's name, `%h` the host, `%u` the user, `%p` the port. The command runs without a shell, a window or any input, for at most 60 seconds, and the first line it prints is the password; nothing of it is logged. FeroSSH shows each command and asks before it runs the first time (the yes is kept in `%LOCALAPPDATA%\FeroSSH`, not with the settings, so a copied settings file cannot run anything unasked). If the password from a source is refused, FeroSSH asks you to type it; one-time codes are always typed.
- **Desktop sessions.** A session's type can be an SSH terminal, a Remote desktop (RDP) or a VNC desktop. An RDP session without "Via SSH" opens Windows' Remote Desktop Connection straight to the machine, for Windows PCs and servers. With "Via SSH" set to another session, FeroSSH logs in there first and tunnels the desktop through that connection (Host empty means the SSH host itself). VNC always goes through SSH and opens in the built-in viewer of the desktop build.
- **Imports from other SSH clients.** File > Import sessions lists the clients that have saved sessions on your account: PuTTY and KiTTY (registry), WinSCP (registry or `%APPDATA%\WinSCP.ini`), MobaXterm (`MobaXterm.ini` in `Documents\MobaXterm` or `%APPDATA%\MobaXterm`), mRemoteNG (`%APPDATA%\mRemoteNG\confCons.xml`) and SecureCRT (its `Config\Sessions` folder). Pick one to see its sessions with a box each, untick what you don't want, and choose Import. *From a file…* reads any of these files from a portable install: a `WinSCP.ini`, a `MobaXterm.ini` or `.mxtsessions` export, a `confCons.xml`, or one SecureCRT or KiTTY session file, which brings the folder it is in. Host, user, port, key file, folders and PuTTY/KiTTY port forwards come over, and so do Telnet sessions (from all but WinSCP) and RDP and VNC sessions from MobaXterm and mRemoteNG. They go into `%APPDATA%\FeroSSH\imported-<client>.conf` (PuTTY keeps `putty-sessions.conf`) in ssh_config syntax, in a folder named after the client. Importing again from the same client replaces that file. Names already used by your `~/.ssh/config`, your saved sessions or another import are left out, and so is what has no SSH, Telnet, RDP or VNC equivalent (raw, rlogin, FTP and the like). Jump hosts (WinSCP tunnels, MobaXterm SSH gateways) come over as the session's jump host. The preview says what does not come over, such as a jump host's own key file or SecureCRT firewalls. A VNC session needs *Via SSH* set with F2, since VNC always goes through SSH. An mRemoteNG file encrypted whole with a master password has to be exported unencrypted first. **Passwords are never imported**: the preview flags the sessions that had one, so you can give them a password source instead. PuTTY `.ppk` key files (v2 and v3) work for Ed25519 and ECDSA P-256; RSA `.ppk` keys work through Pageant.
- **File transfer.** Ctrl+Shift+E shows the focused pane's host over SFTP in the side pane, on the same connection (no second login). Enter opens a folder or downloads a file, D downloads (folders whole), U or Ctrl+Shift+U uploads, Del deletes after asking, Tab moves to the transfer queue (Space pauses or resumes, R retries, X cancels, C clears finished ones). Drop files or folders from Explorer on a pane to upload them to the shell's current folder, after a confirmation. Downloads go to your Downloads folder (`DownloadFolder` in `ferossh.conf` changes it). Three files move at once; a dropped connection pauses the queue and it carries on, from where each file stopped, when you log in again. Session > Verify transfers compares SHA-256 on both ends after each file (the server needs `sha256sum`).

- **ZMODEM (`rz`/`sz`)**, for hosts and console servers without SFTP, over SSH or Telnet. Turn it on with Session > ZMODEM: answer rz and sz (`ZModem yes` in `ferossh.conf`); it is off by default, so their output shows as it is. Then `sz file` on the server saves the file in your download folder (as `name (2)` if one is there already, never overwriting), and `rz` opens a file picker for what to send. Progress shows in the pane, and Ctrl+C cancels. The protocol runs in the sandboxed worker and is fuzz-tested; the window only reads the files you picked and writes into the download folder, and a request to run a command (ZCOMMAND) stops the transfer. Files over 4 GB need SFTP (ZMODEM's limit).
- **Safe file names.** An existing file is never overwritten without asking (Overwrite, Skip or Keep both, Shift for all). A folder download does not follow links that lead outside the folder, and server names Windows cannot hold (`CON`, `a:b`, trailing dots, control characters) are made safe or refused. Partial files are `.part` locally and `.filepart` on the server until complete.
- **Following `cd`.** The file view follows the shell's directory when the shell reports it with OSC 7. fish does by default; for bash, add this to `~/.bashrc` on the server: `PROMPT_COMMAND='printf "\e]7;file://%s%s\e\\" "$HOSTNAME" "$PWD"'`. View > File transfer follows cd (or F in the view) turns it off.
- **Port forwarding.** `LocalForward`, `RemoteForward` and `DynamicForward` in `~/.ssh/config` start when you log in; View > Port forwards (Ctrl+Shift+P) lists every connection's forwards with their state and open connections, adds one to the connection you click in the list, or else the focused pane's (type `-L 8080:db.internal:5432`, `-R 9000:localhost:3000` or `-D 1080`, then Enter) and stops the selected one (Del). All of this works on a live connection, without reconnecting. Enter or F2 on a forward puts it on the add line to change its port or target; a new target on the same port keeps the open connections, and sending a stopped forward back unchanged retries it. `-KL 8080`, `-KR 9000` and `-KD 1080` stop a forward by its port, as `~C` does in OpenSSH. Changes made this way last for the tab's reconnects; the saved session is left as it was. A dynamic forward is a SOCKS proxy speaking SOCKS 4, 4a and 5. Local listeners take `127.0.0.1` and `::1` unless you give an address (`*:8080`, or `GatewayPorts yes`). Forwards live as long as a tab on that connection does. A tab whose connection forwards shows `⇄`, in amber when the server can reach back into your PC (remote forwards or X11).
- **Jump hosts.** `ProxyJump bastion` (or `admin@gw:2222,inner` for several in turn, as `ssh -J` takes them) in `~/.ssh/config`, or the *Jump host* field of the session form, reaches a host through others. Each jump host is a login of its own, in a sandboxed worker of its own: its host key is checked against `known_hosts` and it signs in with its own keys or password, as if you had connected to it. Its worker only opens a TCP stream to the next hop, and the next hop's worker runs its SSH connection over that stream, encrypted end to end, so a jump host (or its worker) never sees the target's keys or what you type there. The pane says where each hop is, and which jump host could not reach the next one and why. `ProxyCommand` (such as `ncat --proxy proxy:8080 %h %p`) runs a local program instead and sends the connection through its input and output; FeroSSH asks once before it runs a command line it has not run before, and shows what the program printed when it fails. `ProxyJump none` or `ProxyCommand none` turns either off for a host.
- **Remote desktop.** Session > Open remote desktop (Ctrl+Shift+D) shows the Linux desktop of the host you are logged in to, X11 or Wayland, through the SSH connection. The server needs an RDP server: xrdp (`sudo apt install xrdp`) or GNOME Remote Desktop. FeroSSH first checks that something answers on the server's RDP port (3389, or `DesktopPort` in the host's profile in `ferossh.conf`) and says so plainly when nothing does; then it forwards a loopback port to it (33900 to 33999, the same one for the same host each time, never 3389) and opens Windows' Remote Desktop Connection there. Nothing new is opened to the network: the RDP port stays closed on the server's firewall, and the tunnel closes with the connection. The desktop opens in its own window.
- **Remote desktop in a tab (optional build).** `ferossh-desktop.exe`, built with the `desktop-viewer` Cargo feature, adds Session > Open remote desktop in a tab (RDP) and (VNC); `rdp-viewer` and `vnc-viewer` build one of the two. They tunnel the server's RDP port (`DesktopPort`, 3389) or VNC port (`VncPort`, 5900) like the remote desktop above and show the desktop in a FeroSSH tab, keyboard and mouse included. For RDP the server needs xrdp or GNOME Remote Desktop; the tab asks for the user name (the SSH user by default) and password, uses NLA where the server has it, and sends keys as scan codes in your keyboard layout. For VNC it needs a VNC server (x11vnc or TigerVNC for X11, wayvnc or GNOME's VNC mode for Wayland). Everything the server sends, RDP's TLS and login included, is handled in a separate viewer process, in an AppContainer with no capabilities at all (no network, files or registry), and checked again before it is drawn. The viewer only ever connects through the SSH tunnel: VNC's own password is weak, and the RDP server's self-signed certificate is not checked against anything, since the SSH host key already identified the machine. RDP uses [IronRDP](https://github.com/Devolutions/IronRDP) and adds about 2.4 MB to the 3.2 MB exe; VNC is FeroSSH's own code and adds about 80 KB. The standard `ferossh.exe` contains none of this code. The desktop takes the size of its pane, also after a split or a divider drag, where the server can change it (RDP Display Control, which xrdp and Windows have; VNC SetDesktopSize, which TigerVNC's Xvnc has); otherwise the picture is scaled to fill the pane. A desktop tab moves into a split like a terminal tab, and it keeps the SSH connection open after the terminal it came from closed, until the desktop closes too. Not yet: clipboard sharing.

- **X11 forwarding.** `ForwardX11 yes` for a host sends X programs on the server to an X server on Windows, such as VcXsrv or X410 (FeroSSH ships none); the X server must listen on TCP. The display is `X11Display` in `ferossh.conf`, else `DISPLAY`, else `localhost:0`. The server gets a fake cookie; FeroSSH checks it on each X connection and puts the real one from `%XAUTHORITY%` or `~\.Xauthority` in its place (none, for an X server without access control). X11 is off unless a host turns it on: X programs on the server can see and type into your other X windows.
- **Per-host look.** View > Font and View > Theme change the focused pane. View > Font offers eight monospace fonts: Cascadia Mono, Cascadia Code, Consolas, Lucida Console and Courier New come with Windows, and JetBrains Mono, Fira Code and Source Code Pro are free downloads (greyed out until installed); Session > Save font and theme for this host keeps them for the next connection.
- **tmux.** tmux is never started for you unless you ask. Session > Attach tmux types `tmux -CC new-session -A -s main` at the pane's shell (typing `tmux -CC` yourself works too), and tmux's windows and panes become native tabs and panes: no status bar, no prefix key, native scrollback with tmux's history in it, and native copy, paste and search. Splits, new tabs and closing panes go to tmux. Session > Detach tmux, or closing the FeroSSH window, leaves everything running on the server; attach again from any PC and the tabs, splits, fonts and themes come back. A dropped connection reattaches after you log in again. Session > Switch tmux session lists the other sessions (also offered right after attaching). Two layouts, kept per session:
  - *One window per pane* (the default; tmux 3.3 or later): every native pane is its own tmux window, so each pane can have its own font, text size and theme. FeroSSH keeps the splits and looks in the session (`@ferossh-layout`). A plain tmux client shows the panes as separate windows.
  - *tmux's own splits* (untick Session > tmux: one window per pane, or older tmux): each tmux window is a tab and tmux's splits are the panes, one font per window; resizing a pane resizes it in tmux.

  To attach on every login to a host, name the session in its profile. GNU screen has no control mode and runs as an ordinary terminal.

  ```
  Profile web1
      Tmux main
      TmuxLayout ferossh
  ```

- **Automatic reconnect.** When a connection drops under an open shell (network gone, Wi-Fi switched, laptop asleep, server rebooted), the tab stays as it is and FeroSSH logs in again on its own, after 1, 2, 4, 8, 15 and then every 30 seconds, for up to 15 minutes; Enter tries at once, Esc stops. The pane keeps its place in the layout, its look, scrollback and log file; port forwards start again, the login script runs again, tmux reattaches with its tabs and splits, and SFTP transfers resume. Tabs that shared the connection open their shells on the new one, so there is still one login. Only a real drop counts: the worker tells a broken connection apart from a shell that exited or a server that ended the session, and a failed login or a changed host key stops the retries. A drop is noticed when the server stops answering keepalives (`ServerAliveInterval`, 30 seconds by default, `ServerAliveCountMax` 3). A password you typed (rather than one from a password source) is asked again. File > Reconnect automatically turns it off; `AutoReconnect no` in a host's profile turns it off for that host only.
- **Host keys.** A new host shows its SHA-256 fingerprint and randomart, and you type `yes` to trust it; the key is saved hashed to `known_hosts`. A changed key fills the window with a warning and cannot be bypassed: if you know why it changed, use Session > Replace host key..., which asks twice. Host certificates work as in OpenSSH: with an `@cert-authority` line for the host in `known_hosts`, FeroSSH asks the server for a certificate and accepts it without a prompt when that CA signed it, the hostname is one of its principals and it is in date. `@revoked` CA or host keys are refused.
- **Sign-in.** Keys are tried from the OpenSSH agent first, then Pageant, then key files (`id_ed25519` and `id_ecdsa` unless the config names others). Key files may be Ed25519 or ECDSA P-256, encrypted or not; the passphrase is asked in the terminal and never kept. RSA keys work only through an agent, need 3072 bits or more, and sign with SHA-2. Agents may also hold ECDSA P-384 and P-521 keys (smart cards often do) and user certificates (`ssh-add` adds `id_*-cert.pub` with its key). Then keyboard-interactive (one-time codes) and passwords.
- **Security keys.** FIDO2 keys (`sk-ssh-ed25519@openssh.com`, `sk-ecdsa-sha2-nistp256@openssh.com`) work from key files (`id_ecdsa_sk`, `id_ed25519_sk`, or any `IdentityFile`) through Windows' own WebAuthn dialog, as Windows OpenSSH does: touch a USB or NFC key, or confirm with Windows Hello. Keys held by the OpenSSH agent work too. `ferossh.exe --new-security-key [--hello] [--ed25519] FILE` makes a new key file, like `ssh-keygen -t ecdsa-sk`; `--hello` makes it with Windows Hello, so no hardware key is needed.
- **Sandbox.** Each SSH connection gets its own worker process, which talks to the network in an AppContainer with network access only: it cannot read your files or keys, and asks the window for every signature. Tabs that share a login share its worker; another host or user gets a worker of its own, so a worker taken over by one server cannot see your other connections. Each jump host on the way gets a worker of its own too. Every sandboxed process runs in a job object (killed with the window, no child processes, memory capped at 1 GiB, no clipboard or other windows) and starts with process mitigations (no Win32k system calls, Control Flow Guard, CET shadow stacks where the CPU has them, no dynamic code, no non-system fonts, mandatory ASLR, strict handle checks, DLLs from System32 first). The window checks everything a worker sends: frame sizes, the order of a real login, and that a sign request is a well-formed login for that user and key. `ferossh.exe --check-sandbox | more` shows what your Windows allows. Windows does not let AppContainers reach 127.0.0.1, so use `--no-sandbox` for SSH servers on the same machine. Forwards to and from localhost work in the sandbox: the window holds those sockets, and the worker parses what arrives (SOCKS requests, X11 setups). [SECURITY.md](SECURITY.md) describes the whole model and its limits.
- **Updates.** FeroSSH never contacts anything but your servers unless you ask. Help > Check for updates asks GitHub for the latest release's update file and its Ed25519 signature, checks the signature against the key built into the exe before reading anything in the file, and says whether a newer release exists; Yes opens its release page. Help > Check for updates weekly does the same once a week, quietly unless there is a new release (off by default; `UpdateCheck weekly` in `ferossh.conf`). Nothing is downloaded or installed for you.
- **Logs.** Session > Log to file writes what the host sends to `%LOCALAPPDATA%\FeroSSH\logs`, one file per tab named by host, tab and time (`host_tab1_2026-10-24_2215.log`). Plain logs keep the readable text, and Session > Timestamp each log line puts the time each line started in front of it (`[2026-10-26 19:24:49.123] $ uptime`); Session > Log raw output keeps every byte, unstamped. Passwords and passphrases never reach the log. Every log is sealed as it is written: `host_tab1_….log.chain` beside it holds a SHA-256 hash chain over the log's bytes (a seal at least every 10 seconds while output comes), and when the log ends its last seal goes into `log-index.chain`, where each line also hashes the one before. Session > Check a log for changes says whether a log is intact, or where it was changed, cut short or added to. This makes edits visible, not impossible: someone using your Windows account could rewrite a log, its chain and the index together, so copy `log-index.chain` somewhere else when a log has to hold up later.

### Colour themes

Built in: Nord (the default), Dracula, Catppuccin Mocha, Gruvbox Dark, Solarized Dark, Tokyo Night, One Dark, Monokai, Rosé Pine, Everforest, Campbell and One Half Light, plus two warning themes: **Production** (muted red background, red cursor) and **Staging** (amber). `ferossh.exe --theme Production prod-db` opens a session in a given theme, which is handy for desktop shortcuts.

The theme follows the host automatically: a host tagged `production`, `staging` or `development` with ssh_config's `Tag` keyword gets Production, Staging or Nord, and your own rules can match host patterns (`*.prod.example.com !prod-sandbox`) or tags, with an optional red or amber tint over any theme. Rules and per-host profiles live in `%APPDATA%\FeroSSH\ferossh.conf`:

```
ThemeRule
    Hosts *.prod.example.com !prod-sandbox
    Theme Production
ThemeRule
    Tags staging
    Theme Nord
    Tint ffb000 40
Profile web1
    Font Cascadia Mono
    FontSize 12
    Theme Dracula
```

`Tint` mixes a colour (hex) into the theme by 0 to 255. A host's profile wins over the rules, and the rules over `--theme`. The palettes are the themes' published terminal colours; all are MIT licensed except Tokyo Night's terminal port (Apache-2.0).

## Design

- Native Win32 with DirectWrite/Direct2D rendering. No Electron, Qt or Java.
- Separate processes: a UI process that never speaks SSH, and one AppContainer-sandboxed SSH worker per connection that never sees private keys or your files. The built-in desktop viewer decodes remote screens in a second AppContainer with no capabilities at all.
- Modern crypto only. Post-quantum `mlkem768x25519-sha256` key exchange first; no SHA-1, CBC, DSA or `ssh-rsa` signatures (see [`crypto_policy.rs`](crates/worker/src/crypto_policy.rs)).
- Older switches, routers and SSH servers that lack those can be allowed per host with `LegacyAlgorithms yes` in the host's `Profile` in `ferossh.conf`. This adds ECDH on NIST curves, DH groups 14 to 18 with SHA-2, AES-CTR and plain HMAC-SHA-2, still with no SHA-1, CBC or DSA. A tab that uses them shows an amber `⚠`, and when a connection fails for lack of them FeroSSH says so. A server without strict key exchange (Terrapin) gets AES-GCM instead of ChaCha20-Poly1305.
- Keys stay in the Windows OpenSSH agent, Pageant, a FIDO2 token or the TPM. FeroSSH keeps no passwords of its own: a password is saved only if you choose Windows Credential Manager as its source, and never imported from other clients.
- Every parser of untrusted input (IPC, terminal, SFTP, ZMODEM, SOCKS and X11, Telnet, tmux control mode, VNC and RDP, key files, sign requests, `ssh_config`, `known_hosts` and session imports) is fuzz-tested on every change and in a weekly campaign.
- OpenSSH `ssh_config` is the session format.

## Building

Requirements: Rust via rustup (the pinned toolchain in `rust-toolchain.toml` installs itself), Visual Studio Build Tools with the MSVC toolchain, and the Windows SDK. No CMake, NASM or extra C toolchain.

```
cargo build --release -p ferossh
```

The release profile optimises for size and links the C runtime statically, so `target\release\ferossh.exe` runs on a clean Windows 10 1903+ machine.

With the built-in desktop viewer: `cargo build --release -p ferossh --features desktop-viewer` (RDP and VNC), or `--features rdp-viewer` or `--features vnc-viewer` for one. CI builds the standard exe, the VNC-only one and the full one, uploads them as `ferossh.exe`, `ferossh-vnc.exe` and `ferossh-desktop.exe`, and reports their sizes.

Checks run in CI: `cargo fmt`, `cargo clippy`, `cargo test`, `cargo deny`, `cargo audit`, SSH tests against a real OpenSSH server on Linux (`cargo test -p ferossh-worker --test sshd`, skipped where `sshd` is not installed), the tmux integration against a real tmux (`cargo test -p ferossh tmux_e2e`, skipped without tmux), the RDP viewer against a real xrdp (`FEROSSH_TEST_RDP="127.0.0.1:3389 user password" cargo test -p ferossh-viewer --features rdp rdp::`), the VNC viewer's resize against a real Xvnc (`FEROSSH_TEST_VNC=127.0.0.1:5905 cargo test -p ferossh-viewer --features vnc resizes_a_real_server`), `ferossh.exe --check-sandbox` on the release exe, a reproducible-build check, and a one-minute fuzz run of each of the eleven fuzz targets (`cargo +nightly fuzz run --target x86_64-unknown-linux-gnu term_feed`). The [fuzz campaign](.github/workflows/fuzz.yml) runs every target for longer each week, keeping its corpus between runs.

Releases: pushing a version tag (`git tag v0.1.0 && git push origin v0.1.0`) runs [`release.yml`](.github/workflows/release.yml). It checks that the tag matches the version in `Cargo.toml` and that `docs/releases/<tag>.md` exists, runs every CI job, and publishes a GitHub Release with `ferossh.exe`, `ferossh-desktop.exe`, `SHA256SUMS.txt`, a release manifest (`BUILD-MANIFEST.json`: tag, commit, toolchain, and each exe's size and SHA-256 before and after signing) and those notes. The exes, sums and manifest get build provenance attestations signed with the workflow's identity, so `gh attestation verify ferossh.exe -R jkobierczynski/FeroSSH` checks a download. Builds are reproducible: `pwsh scripts/build-release.ps1` on a release's tag gives the same bytes as the manifest's unsigned hashes, and CI checks that on every change. With the `UPDATE_SIGNING_KEY` secret set, each release also gets `update.txt` and `update.txt.sig`, the signed file Help > Check for updates reads; `cargo run -p ferossh-update --example keygen` makes that key once, writing the public half to `crates/update/update-key.pub` (commit it) and printing the private half for the secret. Run the workflow by hand from the Actions tab for a dry run: everything but the attestation and the release, with the files uploaded as the `release-dry-run` artifact. Each run also uploads `winget-manifests`, the winget manifests for `ferossh.exe` (package `jkobierczynski.FeroSSH`, a portable app) ready to submit to [winget-pkgs](https://github.com/microsoft/winget-pkgs), for example with `wingetcreate submit`. The exes are signed through SignPath (see [Code signing](#code-signing) below) once the `SIGNPATH_API_TOKEN` secret and the `SIGNPATH_ORGANIZATION_ID` variable are set, and go out unsigned otherwise; the release waits until an approver approves the signing request on signpath.io.

On Linux or macOS, `cargo run -p ferossh-term --example vttest -- 1 2 8` drives [vttest](https://invisible-island.net/vttest/) through the emulator and prints every screen as text.

## Reporting a vulnerability

Please report security problems privately through **Report a vulnerability** on the repository's [Security tab](https://github.com/jkobierczynski/FeroSSH/security), not in a public issue. [SECURITY.md](SECURITY.md) says what to include and what to expect.

## Code signing

Release exes are not code signed yet. Each release is built from this repository by the [release workflow](.github/workflows/release.yml) on GitHub's runners, reproducibly, and its exes, `SHA256SUMS.txt` and `BUILD-MANIFEST.json` carry build provenance attestations, so a download can be checked against this source (see [Verifying a download](docs/guide/verifying-downloads.md)). Once signing is set up, only `ferossh.exe` and `ferossh-desktop.exe`, built by that workflow from this project's own source, will be signed, each after the [owner](https://github.com/jkobierczynski) approves the request.

**Privacy policy:** This program will not transfer any information to other networked systems unless specifically requested by the user or the person installing or operating it. FeroSSH connects only to the servers you tell it to and sends no telemetry.
